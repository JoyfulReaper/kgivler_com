Contact forms need more than a POST endpoint

A contact form starts small, then grows validation, abuse controls, persistent storage, notification delivery, and administration. HappyContact takes care of that backend work while letting each website keep its own design and user experience. I built it to use in client website projects, rather than rebuilding the same backend for every site.

My own development-services website is the first real deployment. Its Go form forwards accepted messages to a local HappyContact instance written in .NET.

What it does

Validated submissions

An ASP.NET Core API handles contact details, validation, and abuse protection before accepting inquiries.

Durable delivery

SQLite stores submissions and per-destination jobs, so a notification is not the only record of an inquiry.

SMTP and ntfy

Background workers deliver complete messages by email and concise notifications through ntfy, with delivery status and failure handling.

Private administration

An access-restricted admin interface manages sites, notification destinations, and received messages.

How the live setup works

The public form stays on the website domain. The website server forwards the validated submission locally. HappyContact stores it and queues delivery before acknowledging acceptance; notifications run separately in background workers.
